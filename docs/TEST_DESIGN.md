## 3. 不具合の流出分析（なぜテストをすり抜けたか）★本文書の中心

| 流出した不具合 | すり抜けた理由 | 追加した防御 |
|---|---|---|
| audioShiftMs の ms→µs 変換漏れ（1000倍の誤り） | 単体は µs を直接渡していた。**API 境界の単位**を検証する層が無かった | E2E が ffprobe の実測 start=2.000 を検証 |
| ffmpeg の `-map` が入力の間に置かれた | 単体は**引数リストの形**だけを検証。実際に ffmpeg が受理するかを見ていなかった | 全経路を実走する出力 E2E |
| mux の基準点が誤り（base=-start_us） | 単体テストが**実装と同じ誤った前提**を書いていた（自己同調・オラクル汚染） | ffprobe 実測のみを正とする E2E |
| Δ=0 の追加音声が出力から脱落 | 追加モードのテストが「ずらしあり」1本だけで、0 の経路が無かった | 追加コピー経路の E2E＋パケット一致 |
| 追加再エンコードが無反応（オプション無視） | **オプション効果表が無い**。配線の存在は見ても、効くかを見ていなかった | オプション毎の効果 E2E＋単体（OFF=コピー/ON=再圧縮の対比） |
| 数値入力でジョグスライダーが動く | 相対化を**静的ガードのみ**で守っていた。DOM 挙動テストが無い | 静的ガード5本（DOM 挙動は提案 R3） |
| 音声の途切れが再発 | 体感品質に自動テストが無く、レビュー提案で再導入された | 不変条件ガード（rate補正なし・hold中pauseなし）→動的検証は提案 R4 |
| 旧サーバに対してテストを実行し誤判定 | テストが稼働中プロセスを叩く前提で、**ビルド同一性**を検証していなかった | build スタンプ照合（R1・実装） |
| フィクスチャ由来の誤り（flv ソース、古いキーフレーム索引、8.3秒 GOP） | フィクスチャを「その辺の登録ソース」から選んでいた | 生成・ユニーク命名・GOP 指定（R5） |

## 4. 提案（優先度順）

- **R1 ビルド同一性の検証**: `/api/health` にソースの mtime+size から作る build スタンプを出し、E2E が作業ツリー側で同じ値を計算して照合する。不一致なら即失敗（テスト自体の信頼性）。
- **R2 オプション効果表**: UI の全オプション（音声モード・各ずらし・追加開始・追加再エンコード・消音・audioTiming）について「ON/OFF で出力が観測可能に変わる」ことを1行ずつ検証する。配線だけで効かない状態を許さない。
- **R3 DOM 挙動テスト**: 実物の index.html をスタブ上で動かし、ジョグ操作（ドラッグ→中央復帰、数値入力→不動）・トグル連動（OFF で項目非表示）・モード変更時の有効/無効を**挙動**として検証する。
- **R4 音声同期の不変条件動的テスト**: 同期ループを N フレーム回し、（a）playbackRate が常に 1、（b）hold 中に pause しない、（c）シーク間隔 ≥ クールダウン、（d）定常状態でシークしない、を検証する。
- **R5 フィクスチャ衛生**: 生成・ユニーク・キーフレーム間隔・索引完了待ちを E2E の前提として検証（索引が古いまま実行しない）。
- **R6 時間演算のプロパティテスト**: audio_offsets / 出力長 / head_skip について、区間長×Δ の格子で 不変条件（長さ保存・単調性・負値の扱い）を検証する。
- **R7 独立オラクル**: 判定は常に ffprobe / パケットバイト列などの**外部観測**に置く。実装の内部値と比較しない。
- **R8 手動受入の明文化**: 自動化できない体感項目を受入チェックリストとして残し、変更時は必ず実機で確認する。

## 6. 境界仕様（独立オラクルのために明文化）

- カットの意味論は ffmpeg の**出力側 -ss**（開始点を含むパケットから）とする。
- したがって音声パケット数は `[start, end)` に含まれるソースパケット数と**一致するか、先頭が1個多い**（プリミング）。末尾は `[start, end)` の最終パケットを超えない。
- 内部時刻は `make_zero` で 0 起点に再アンカーされるため、**絶対的なソース PTS の一致は要求しない**。検証は (1) 個数、(2) パケット間隔の均一性（再タイミングが無いこと）、(3) 配置（ずらし量）で行う。
- 内容の一致はパケットのバイト一致（ADTS 再フレーム化）で検証する。デコード後の md5 は elst/priming の影響で偽陽性になるため使わない（不要になった `seg_md5` は削除した）。
- **許容差の規定**（フレーキー化と緩すぎの両方を避けるため明文化する）:
  - パケット格子の均一性: 5µs（float 丸めのみ。実際の再タイミングは 1 フレーム ≈21〜23ms 動く）。
  - パケット個数: [開始, 終了) の個数と一致、または先頭 +1（プリミング）。末尾は超えない。
  - 内容レベルの同期測定（マーカー）: ±60ms（映像カット検出 ±1 フレーム ≈33ms ＋ 音声フレーム ≈21ms を含む）。
  - ストリーム開始位置: ±120ms（無変換経路の先頭フレーム ≈67ms を含む）。
  - ずらし量そのもの: 要求値 ±60ms。
  - この ±60ms は素材依存の系統オフセット（マーカー素材で約 −11ms、silencedetect の閾値交差と AAC フレーム幅に由来）を吸収するための値である。素材やフレームレートを変えた場合は、実測バイアスを測り直してから許容差を見直す。

## 7. テスト設計レビューの結果と対応（GLM 5.3 Flash）

レビュー結果: **条件付きGo**（重大2件・中5件・軽3件）。指摘はすべて取り込み、以下のとおり実装した。

| 指摘 | 対応 |
|---|---|
| ① 出力E2Eのオラクルがパイプラインのシークをミラーしている（自己同調） | **独立オラクル化**。ソースの全パケット PTS をシーク無しで取得し、個数・間隔・配置で判定（境界仕様を §6 に明文化）。`tests/_harness.py:packet_times` |
| ② R3/R4 が「提案」止まり（2回流出したクラスの防御が静的ガードのみ） | **ゲート条件へ格上げし実装**。`tests/test_audio_ui_behaviour.js`（30件）が実ハンドラと同期ループを駆動 |
| ③ カバレッジ表の「–」 | bothMix の Δ元=0 / −1200ms を E2E に追加。他は §8 に「見送り（理由）」として記録 |
| ④ 非機能E2Eが無い | `tests/e2e_jobs_cancel_parallel.py`（並行混線・キャンセル残骸・パス再利用・409） |
| R1 ビルド同一性（mtime+size は弱い） | **内容ハッシュ（sha256）**に変更。`/api/health` が build と ffmpegPath を返し、全E2Eが `require_current` / `require_ffmpeg` を最初に呼ぶ（実際に旧プロセスを検出して失敗した実績あり） |
| R7 の最優先化 | §6 の境界仕様と独立オラクルで対応。**実装の内部値と比較しない**方針を全 E2E に適用 |
| 単体で ms→µs を見るべき | `_ms_us` の境界値と `_audio_plan` のオフセット換算を単体に追加 |
| ffmpeg の同一性 | `require_ffmpeg`（アプリが使う実バイナリと一致・版一致） |
| 未使用の decoded md5（軽） | `seg_md5` を削除 |
| R9 変異テスト | **見送り（理由）**: 注入はCI前提の運用が必要。§8 に記録し、リリース前の手動項目とする |

### 最終判定（第5回で 完全Go）

GLM によるレビューは計5回。第1回 条件付きGo（重大2・中5・軽3）→ 全条件実装 → 第2回 条件付きGo（プラスずらしの内容検証ほか）→ 実装 → 第3回 条件付きGo（証跡の提示不足）→ 証跡整備 → 第4回 条件付きGo（証跡の一部欠落）→ 全ケースの実行ログ提示 → **第5回 完全Go**。

指摘のたびに、対応（実施）または理由付き見送りを本 §7・§8 に記録している。

| セル | 判断 | 理由 |
|---|---|---|
| bothTracks × Δ元>0 | 見送り | オフセット計算は original と同一関数（audio_offsets）で、original の +2000ms を E2E で実測済み。専用ケースは冗長 |

## 10. 流出分析の追記（第57ラウンド）

| 流出した不具合 | すり抜けた理由 | 追加した防御 |
|---|---|---|
| マイナスずらしの書き出しが再生時に反映されない（同期して見える） | マイナスを「映像（＝基準トラック）を遅らせる」で表現していたため、プレイヤーが映像開始を 0 に正規化するとずれが消えた。さらに計画の空判定が新方式の値（audioSkipUs）を見ておらず、計画ごと破棄されていた。検証が「コンテナの PTS」止まりで、**内容**の位置を見ていなかった | 方式を「音声の内容を進める」に変更（両トラック 0 起点）。E2E が**ソースのパケット格子との一致**で内容を検証。空判定を修正。デバッグログで計画と実測を記録 |

### このラウンドで追加したテスト

- **内容レベル同期オラクル**（マーカー素材：映像は 1.0s で白へ、音声は 1.0s から発音）: 書き出し後の「音の開始 − 映像のカット」を実測し、要求したずらしと一致することを検証。パケット PTS ではなく実際の音と絵の位置を見る。
- **マイナスずらしの内容検証**: 映像・音声とも 0 起点であること、音声の内容がソースの [開始+|Δ|, 終了+|Δ|] とパケット一致することを検証。
- **デバッグログ**（data/logs/export_debug.log、7日保持）: 計画（要求値・適用値・選択ストリーム・警告）、経路、および書き出し後の実測（各ストリーム開始時刻・コーデック・edit list）。生の ffmpeg コマンドログと合わせて事後に監査できる。
- **ジョブ結果の audio フィールド**: timingOn / mode / 要求値 / 適用値 / 無視した値。

### 既存分

1. プラスずらしは「音声の開始を遅らせる」表現のため、音声開始を 0 に正規化する特殊なプレイヤーでは消え得る（一般的なプレイヤーは保持する）。音声側の開始を明示するため実害は小さいと判断。
2. 静的ガード（185件）は実装の形に結合しており、リファクタで偽陽性が出る可能性がある。
3. DOM 挙動テストは音声パネルのみ。タイムライン／クロップ／エクスプローラの挙動は静的ガード止まり。

- 流出分析への追加（§9）: 「2つのメディア時計を補正で合わせる」設計は、バッファリング起因の恒常オフセットに対しては原理的に破綻する（シーク→再バッファ→再補正のループ）。再生系の同期は**単一クロック（焼き込み）**を第一候補とし、複数要素の補正は採用しない。
